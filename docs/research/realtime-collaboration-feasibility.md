# Realtime collaboration feasibility

Investigated 2026-10-22. The initial assessment used source inspection and primary documentation. The user subsequently approved implementation with the scope below; ongoing implementation and test evidence are recorded in [the implementation record](collaboration-implementation.md). No actual Steam session has been validated.

## Assessment

Realtime co-writing, remote cursors, and complete project synchronization are technically feasible. The selected direction is one collaboration model with a hosted-server adapter in both desktop editions and additional Steamworks connectivity in the Steam edition. Each adapter must respect its service's protocol. Steam handles connectivity and identity; Novalist must implement document merging, project synchronization, permissions, persistence, and recovery. The largest integration risk is Novalist's current editor model.

The user clarified that non-Steam clients would connect outbound to a hosted server and identified the community [novalist-sync-server](https://github.com/QF0xB/novalist-sync-server) implementation. This provides a concrete route around requiring reachable writer desktops. The user also confirmed that invited collaborators must be able to work while the project owner is offline; [ADR 0003](../adr/0003-hosted-project-availability.md) records this requirement.

Steam and non-Steam users must be able to collaborate through that same service. Use the existing server unchanged as the integration baseline, and propose focused upstream changes only when implementation demonstrates a missing server capability. [ADR 0004](../adr/0004-shared-hosted-collaboration.md) records this direction. It does not guarantee that the complete feature can ship without any server changes.

Confirmed scope also includes:

- Steamworks sessions that need no hosted project server and require their hosting writer to remain online.
- Sharing the entire project, including all books/drafts, Codex entries, project metadata, images, research, and other project content. Personal application settings remain local as in the scope question; sharing a project does not imply copying application credentials or installed executable extensions.
- No application-imposed upper limit on collaborators. Initially validate with 2–4 simultaneous writers and measure larger groups as capacity testing grows. This is a test target, not a participant cap or a promise of unbounded infrastructure capacity.
- Initial disconnected editing covers already-synchronized prose. Structural changes, asset changes, membership changes, and project snapshot restores require connectivity. This narrower scope is accepted to keep complexity manageable; merge and durable recovery still require validation.
- Collaborators retain usable local copies after a session ends and can edit all project content while participating. Only the owner manages membership and deletes the shared project.
- Hosted invitations use single-use links that require sign-in. The link admits one account, with retries by that account allowed; other accounts cannot reuse it.
- A project uses one collaboration connection mode at a time. Users fully close one session and start another; there is no dedicated mode-switch feature, automatic handover, or cross-session reconciliation.
- A scene deleted concurrently with another writer's edits stays deleted in the shared project; those edits are preserved in a recovered scene copy. [ADR 0005](../adr/0005-retain-collaborator-work.md) records retention and recovery behavior.
- Any collaborator may create an independent project from their retained copy, become its owner, and leave the original shared project unaffected.
- Extend Novalist's existing editor with the collaboration support it needs while preserving its behavior and features wherever possible. An editor replacement is outside the selected approach; [ADR 0006](../adr/0006-extend-existing-editor-for-collaboration.md) records this constraint.

Steam distribution is plausible, but its acceptance is unconfirmed. Valve lists eligible software categories without explicitly including writing applications. [Nimble Writer](https://store.steampowered.com/app/348200/Nimble_Writer/) is a real writing-app precedent, not assurance that Valve will accept a new submission. Confirm Novalist's eligibility independently of the hosted-server route. [Steam Direct](https://partner.steamgames.com/steamdirect/)

| Requested capability | Feasibility and remaining work |
| --- | --- |
| Simultaneous prose editing | Feasible with a shared document model and an editor binding that merges operations. Broadcasting saved HTML is insufficient. |
| Remote cursors and selections | Feasible as ephemeral presence, with positions anchored to the shared document. |
| TCP for local tests | Straightforward; loopback tests can exercise the same session protocol as Steam. |
| Hosted connections for Steam and non-Steam Internet users | Both editions connect outbound to the same service. The community server uses SignalR/MessagePack; client integration and the complete collaboration lifecycle remain necessary. |
| Steam friends joining | Lobbies/invitations plus modern Steam networking provide suitable building blocks for sessions that require their hosting writer online and no separate hosted project server. |
| Joining without matching Git commits | Feasible with a consistent project snapshot, asset transfer, and subsequent change catch-up. |

These are engineering assessments based on the sources below, not verified Novalist capabilities.

## What Steam supplies

Use `ISteamNetworkingSockets` or `ISteamNetworkingMessages`; the older `ISteamNetworking` API is deprecated. Modern APIs support reliable delivery and relay connectivity. Lobbies support membership and invitations; keep high-frequency edits and cursors in the collaboration transport rather than lobby metadata. [Networking](https://partner.steamgames.com/doc/features/multiplayer/networking), [lobbies](https://partner.steamgames.com/doc/features/multiplayer/matchmaking)

Ordinary Steam P2P can use Steam Datagram Relay. Extending that relay service to non-Steam users has additional conditions: a version shipping on Steam, a coordinator that issues credentials, and discussion with Valve for the relevant SDKs and availability. Valve does not promise perpetual non-Steam availability. The open-source networking library does not grant access to Valve's relay network. [SDR requirements](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay)

The confirmed hosted-server mode in both editions provides a common route for mixed Steam/non-Steam groups. A separate raw TCP adapter for local tests would need framing and, if exposed remotely, authentication and encryption. The hosted service's SignalR protocol already supplies its message framing. [TCP specification](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2), [TCP security](https://www.rfc-editor.org/rfc/rfc9293.html#section-7), [server setup](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Server/Program.cs)

Steamworks initialization requires the Steam client, an identified application, and an account licensed for that application. Novalist needs a native binding and platform runtime packaging. AppID `480` appears in Valve's development example; it is not Novalist's production identity, and that example alone establishes no unrestricted pre-partner SDK entitlement. The development `steam_appid.txt` must not ship in Steam depots. [API integration](https://partner.steamgames.com/doc/sdk/api)

A TCP prototype can precede onboarding. Validating the actual Steam product requires its app/account setup and separate accounts for collaborating users. Steam Direct currently charges $100 USD per product, with first-release waiting and review requirements; plan that as a separate release dependency. [Steam Direct](https://partner.steamgames.com/steamdirect/), [lobby authentication](https://partner.steamgames.com/doc/features/multiplayer/matchmaking#authentication)

## What the repositories establish

Novalist uses a custom `contenteditable` iframe and sends complete HTML through its save path, with a two-second autosave delay. Replacing editor content resets caret/undo state; the synchronization hook explicitly avoids replacing local echoes for this reason. The expected-hash guard rejects conflicting disk writes instead of merging concurrent edits. A network adapter alone cannot turn this into co-writing. [Editor](../../app/src/renderer/public/editor/editor.html), [input](../../app/src/renderer/public/editor/content-input.js), [synchronization](../../app/src/renderer/src/views/editor/useEditorSynchronization.ts), [persistence](../../app/src/renderer/src/stores/projectPersistence.ts), [conflict guard](../../Novalist.Core/Services/SceneConflictGuard.cs)

Projects contain HTML, JSON metadata, annotations, and assets. Current project services also maintain active book/draft state, while extensions and suggestions can write scene content independently. These paths must participate in collaboration or be explicitly restricted during sessions. Independent participant navigation needs attention too. [Project layout](../manual/03-projects-and-books.md), [project service](../../Novalist.Core/Services/ProjectService.cs), [extension writes](../../Novalist.Backend/Extensions/HostServices.ProjectAccess.cs), [suggestion writes](../../Novalist.Backend/Rpc/SuggestionsRpc.cs)

Fireplace provides a useful transport seam, real Steam sockets code, and Yjs integration. Its TCP implementation binds loopback and rejects remote addresses: it demonstrates same-machine testing, not Internet connectivity. Both its transport and presence model assume two participants. [Transport](../../../Fireplace/src-tauri/src/collab/transport.rs), [loopback](../../../Fireplace/src-tauri/src/collab/loopback.rs), [Steam](../../../Fireplace/src-tauri/src/collab/steam.rs), [document model](../../../Fireplace/src/collab/ydoc.ts)

Fireplace shares selected sections while leaving others unsynchronized. Its Git commit check provides a common baseline for those omitted sections. Disabling that check does not add full-project synchronization. The host seeds the initial Yjs document, and disconnect destroys that session's document and undo manager. There is no retained reconnect/catch-up lifecycle to transplant. ## Community hosted server

Inspected `QF0xB/novalist-sync-server` at commit `199201abad46dc451d2b7d19076cdd894146e26d` on 2026-10-22. It already implements a durable update relay, with ASP.NET Core SignalR, MessagePack, PostgreSQL, and JWT authentication. A Novalist adapter would speak SignalR rather than directly send the local test protocol to a raw TCP socket. [Startup](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Server/Program.cs)

The implemented hub registers authenticated connections, creates projects, checks project membership and write access, broadcasts pushed updates, and streams stored updates after a supplied server sequence. The update log atomically assigns a project sequence and stores each envelope, accepts identical retries, and rejects conflicting reuse of a sender sequence. Its stored update payloads are opaque to the server. This supplies useful delivery and recovery infrastructure; merging text and maintaining an editor remain client responsibilities. [Hub](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Server/Hubs/SyncHub.cs), [update log](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Server/Updates/UpdateLog.cs)

Snapshots and presence are defined as message types, but the current write path explicitly accepts only `Update`. Complete project checkpoints, asset transfer, client encryption/key handling, and cursor presence are not delivered by those enum values. The exposed API also lacks the complete invitation/member-onboarding flow. The design document proposes a Yjs client and further storage features; its implementation phases distinguish those plans from the completed server skeleton and contracts. No corresponding SignalR/Yjs sync client was found in the inspected Novalist checkout. [Protocol types](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Contracts/Protocol.cs), [hub contract](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Contracts/ISyncHub.cs), [design](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/docs/design.md)

These gaps require a capability-by-capability check during integration. Identify which behavior belongs in the client, which can use the existing opaque update protocol, and which genuinely needs a server change. Keep any necessary server patch focused on the demonstrated gap and prepare it for upstream review once its behavior and validation are concrete. No server modification or upstream submission has been made during this investigation.

Tests cover authorization, relay/catch-up, retries, and concurrent sequencing against PostgreSQL. Their SignalR clients use an in-memory test server with long polling; generated payload bytes do not exercise real document merging or client encryption. No live deployment was tested during this investigation. [Hub tests](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/tests/Novalist.Sync.Server.Tests/Hubs/SyncHubTests.cs), [test server](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/tests/Novalist.Sync.Server.Tests/Infrastructure/SyncServer.cs), [test data](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/tests/Novalist.Sync.Server.Tests/Infrastructure/TestData.cs)

## Proposed synchronization model

Keep three separable layers: editor/document merging, session/project synchronization, and transport. Yjs is a candidate: its providers support different protocols, its binary updates converge after all updates arrive, and state vectors identify missing changes. Add a schema-aware rich-text binding to the existing editor; treating raw HTML as shared text can merge markup into invalid structures. Preserve Novalist's formatting, annotations, custom spans, IME input, and undo wherever possible. The selected approach extends the current editor; replacing it would require revisiting the design after identifying a concrete limitation. [Editor bindings and providers](https://docs.yjs.dev/getting-started/a-collaborative-editor), [document updates](https://docs.yjs.dev/api/document-updates)

Use independently synchronized documents for scenes and other editable prose, stable object IDs for project structure, and explicit commands for metadata, rename, reorder, and deletion. Presence should carry participant identity, current document, and stable selection anchors separately from persisted project data. Yjs documents awareness as ephemeral information that disappears when users disconnect. [Awareness](https://docs.yjs.dev/getting-started/adding-awareness)

A proposed hosted-project join sequence replaces Git pinning. The confirmed availability requirement means joins must obtain shared project data from the hosted service after initial publication. The community server's current update log still needs the complete checkpoint and asset lifecycle to meet this requirement.

1. Authenticate the invitation, check protocol/schema compatibility, and authorize the guest before transferring content.
2. Publish a consistent initial project checkpoint, including pending editor changes, with a manifest of IDs, relative paths, sizes, and hashes. Later joins retrieve a published checkpoint from the service without needing the owner online. Include agreed project content and assets; exclude credentials, executable extensions, local preferences, and unrelated history.
3. Transfer missing content in bounded chunks to a guest session directory. Validate paths and hashes; leave existing guest projects untouched.
4. Establish live delivery and catch up on changes after the checkpoint revision, handling overlap and gaps. Install the checkpoint and apply those changes before enabling guest editing. Adopt shared document identity and history rather than independently seeding duplicate content.
5. Persist acknowledged shared updates and the necessary checkpoints/assets independently of the owner. Distinguish local edits, server acknowledgement, and local HTML/JSON files. Reconnect using retained document state and revision information, or perform a fresh snapshot when incompatible.

This is a proposed implementation of the accepted availability requirement, not existing behavior. External file changes, AI edits, extension writes, restores, and structural changes need shared commands and explicit conflict policies. An allowlisted snapshot and resumable asset transfer are new work; a whole-folder backup is not a consistent live synchronization protocol. Steam sessions use a desktop host and a related join flow. Live collaboration ends when that host is unavailable, while participants retain their local copies. Keep concurrent edits to a deleted scene in a recovered scene copy. A fully closed session and a newly started session have no automatic handover or reconciliation; normal closure preserves local work, and session identity prevents pending updates from being replayed into the wrong session.

## Initial disconnected editing

Limited disconnected editing is a reasonable incremental target once durable collaborative document state exists. Yjs can merge delayed or repeated updates and identify missing changes using state vectors. Persisting that state is a separate responsibility: saving only rendered HTML does not preserve the shared document's history and identity. This is an engineering assessment, not a verified Novalist feature. [Document updates](https://docs.yjs.dev/api/document-updates), [offline persistence](https://docs.yjs.dev/getting-started/allowing-offline-editing)

Safe online collaboration already needs a durable outgoing queue, stable update identity, acknowledgements, retry handling, and crash recovery: a connection can drop after the server stores an edit but before the acknowledgement arrives. The community design includes this client machinery, and its server handles duplicate retries and catch-up. The client implementation still needs to be built. [Durability design](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/docs/design.md#L312), [update log](https://github.com/QF0xB/novalist-sync-server/blob/199201abad46dc451d2b7d19076cdd894146e26d/src/Novalist.Sync.Server/Updates/UpdateLog.cs)

Accepted initial scope: allow disconnected editing of already-synchronized prose, with durable pending changes and automatic reconnect to the same session. Require connectivity for creation/deletion/reordering, asset changes, membership changes, and restoration of project snapshots. Whole-project sharing remains the connected scope. Revalidate access, keys, schema, and session identity before replay. Preserve work that cannot be applied, including the approved recovered-copy behavior for concurrent scene deletion. A disconnected Steam guest waits for the session host. Resuming the same session after host restart requires persisted shared state; fully closing that session and starting a new one does not automatically replay its pending updates.

## What to prove before committing to implementation

First build a narrow experiment that adds a collaborative document binding to the existing editor: two participants editing the same rich-text scene, stable remote selections, independent undo, and consistent persistence. Include overlapping typing, formatting, IME composition, comments/footnotes, and interrupted connections. Validate the accepted limited disconnected-editing scope with concurrent edits, restart recovery, and project deletions. Verify that fully ending a session preserves local work and prevents its pending updates from reaching a different session. Exercise the community server's SignalR update/catch-up flow, then prove joining a populated project while writers keep editing, including missing assets and failed transfers. Validate 2–4 writers initially, without encoding that range as a product limit. Finally exercise the shared collaboration model through packaged Steam builds on separate machines/accounts. Passing local or hosted-server tests cannot establish Steam integration.

Hosted connections, mixed Steam/non-Steam collaboration, whole-project sharing, owner-independent hosted availability, and Steam sessions requiring their host online are confirmed requirements. There is no application-imposed participant cap. The existing community server is the integration baseline, with upstream changes only as needed. Local-copy retention, independent copies, full editing with owner-controlled access, separate sessions for the two connection modes, and recovery copies for concurrent scene deletion are settled. Limited disconnected prose editing and extension of the existing editor are the selected approach. Remaining engineering work is to validate the editor binding and recovery model, map client requirements to the server's actual capabilities, and identify any necessary upstream changes. No application implementation has been made during this investigation.
