Give the story more room. Give every action a clear place.

Novalist has strong writing capabilities and a distinctive identity. Its main design problem is that navigation, metadata, formatting and administration often compete at the same level. This proposal keeps the ink-and-gold palette and literary reading surfaces while making the working interface easier to scan, operate and resize.

Revision 02: your requirements

System sans for working controls is the chosen direction. Retain serif manuscript reading and book covers, user-selected editor fonts, and a flat visual treatment using solid surfaces, restrained borders and minimal elevation.

The start screen stays a bookshelf. Preserve named shelves, cover artwork, grouped volumes, selected-book details, cover sizing, sorting, search, reordering, removed-item recovery and the scratchpad.

Scene details contains the complete context sidebar. Context, Footnotes and Inbox remain first-class sections. Notes provides access to synopsis, goal/outcome, narrative timing, explicit cast and custom fields while the existing notes dock and snapshot command stay available.

Reorganization must preserve feature and data depth. The first mockup simplified populated views too aggressively. Its small dataset also concealed long lists and conditional panels. Any field, specialist panel, extension contribution or operation absent from a sample remains required until explicitly discussed; visual approval does not authorize its removal.

Implementation gate: feature parity

  1. For each view, map every current field, action, conditional section, extension slot and persisted preference to its proposed location. Use the source component, actual schema and relevant manual; manual headings alone are not a field-level completeness proof.
  2. Review populated, empty, long-content, custom-schema, overridden and failure examples. Distinguish absent data, a collapsed section, filtered data, a missing provider and a removed capability.
  3. Verify reading, editing, save/undo, links, history and round trips against the existing app. Grouping fields cannot drop them from storage, exports, search, peeks or custom types.
  4. Any unmapped capability blocks that view’s implementation. Record it and resolve its placement before replacing the view. No field removal or data-model simplification is approved.

The per-screen inventories below combine the current documentation with the audited source touchpoints. The richer mockup demonstrates the full sidebar, bookshelf and deeper Dashboard/Codex/Research/Export examples. It is still a design reference; it does not emulate every backend operation.

Built and launched the Electron renderer from checkout 5fdf8a86. Inspected all 25 built-in MainView destinations, plus Library, update dialogs, focus mode, command palette, all four manuscript subviews and seven additional Settings sections.

Used a temporary copy of The Silent Shadows: 22 chapters, 116 scenes, 48 characters, 30 locations and 76 gallery images. The original project was not opened for mutation. A fresh settings directory and Chromium profile kept the review separate from the user’s running workspace.

Actual window geometry

Windowed: 1,440 × 960 outer window, 1,424 × 895 renderer. Smaller editor check: 1,280 × 800 outer, 1,264 × 735 renderer.

Maximized through the Windows window manager: 2,560 × 1,391 renderer on a 2,560 × 1,440 work area. BrowserWindow.isMaximized() returned true. Every main view was captured in this state.

The project uses German UI, a 29 px editor font and bottom-anchored typewriter scrolling. These preferences were retained during inspection. The first-run walkthrough was dismissed and view introductions were marked seen to inspect settled layouts.

Limits: Windows only; no live installer, remote Git operation, extension install, voice generation or export was run. The temporary copy excludes .git, so Git was inspected in its no-repository state. Plot grid, planning board, languages and installed extensions were empty in the inspection context. A concrete design system for this proposal

Identity and typography

Keep Ink Night, Vellum Panel, parchment text and gilt accents. Keep a literary serif for book titles and manuscript reading. Use the user-selected OS-native sans serif for controls and navigation: Segoe UI on Windows, system UI on macOS, Noto Sans fallback. This direction was selected in review 02; serif manuscript text remains.

The mockup’s UI type switch keeps literary serif available for comparison; system sans is the chosen default. In production retain Fraunces/Newsreader for their approved roles, user-selected editor fonts, CJK fallbacks and custom theme compatibility.

Proposed UI: 14 px body, 12 px nonessential metadata, 16 px subsection labels, 24 px view title; optional comfortable density raises UI text to 15–16 px. Ordinary controls 34 px high; compact controls at least 28 px, with pointer targets meeting 24 px or justified exceptions.

Geometry and semantics

Use semantic tokens for every surface, foreground, field border, focus ring, control height and spacing. Reuse the current token contract; adjust aliases deliberately rather than replacing the brand layer. Mockup tokens are scoped to these review files.

Selected navigation uses text, a surface and a rule. Status uses text as well as color. Reserve gold fill for the primary action. Use Lucide-compatible SVG geometry throughout.

Standard toolbar grouping: title/context → primary action; second row for local view modes and frequently used filters. Less-used controls go into named disclosures. Keep native title/menu behavior and platform-specific dialog button ordering.

Update flow: preserve the safety checks, change the interruption

Available → user reviews → background download → ready → user requests installation → save/backup checks → platform handoff.

A dismissal hides the notice for the session; Updates remains reachable through About/Help and the status action. Do not automatically open release notes while somebody is writing. Extension updates use separate rows and per-item status instead of sharing an ambiguous all-current result.

Download and installation must be separate states before background operation is safe. The current AppShell.tsx already checks pending writes, a backend barrier, scene conflicts, detached panes and close backup. Preserve and re-run those checks at installation time; also define how active export/narration/Git work blocks or delays handoff. Retain platform-specific manual handoff and Mac App Store behavior.

Persist downloaded-artifact metadata only if supported by updater validation. Bind installation to the actual verified download token, never an arbitrary renderer path. A download failure offers retry; a save conflict returns to the affected content; an installer failure keeps the app open with actionable detail.

Implementation plan after design approval

Complete the per-view feature-parity mapping above first. Then use small, reviewable changes with explicit regression boundaries. The order below fixes correctness first, then applies the shared shell and view patterns. It does not require replacing the editor or the data model.

Phase 1 · Interaction correctness and readable primitives

Accessible dialogs, truthful states, semantic text and controls

Build/reuse a modal primitive with focus containment, initial/return focus, an inert background and safe dismissal. Split update check results into success/current/offline/error. Introduce readable semantic label and helper-text roles; normalize button, input, focus and disabled states.

Touchpoints: styles/tokens.css, styles/base.css, shell/UpdateDialog.tsx, shell/shellDialogs.css, shell/AppShell.tsx and reusable dialog components.

Done when: keyboard cannot reach the obscured workspace, manual offline checks cannot claim current, normal labels meet contrast targets, and custom themes/high-contrast behavior remain intact.

Phase 2 · Shell and writing workspace

One navigation model with more room for writing

Implement approved mode placement and combined navigation/binder panel. Add shared ViewHeader, ViewToolbar, TaskActions and context-panel patterns. Preserve existing MainView IDs, command registry, extension contributions, split-pane layouts, selection, drafts, detached windows and deep links. Keep native menus and rebindable hotkeys.

Touchpoints: shell/ModeRail.tsx, ModePanel.tsx, modes.ts, Toolbar.tsx, Binder.tsx, ContextPanel.tsx, MainArea.tsx, stores/shellStore.ts, stores/layoutStore.ts. Adapt EditorFrame chrome without rewriting its editor.

Done when: every built-in and extension view stays visibly reachable; resize/maximize, split and restore preserve content and focus; 1,280 px writing has no toolbar clipping. Existing saved layouts migrate without erasing preferences.

Phase 3 · Core daily work

Dashboard, manuscript, Codex and research

Reorder Dashboard around resume/recent work. Give manuscript modes their own suitable space. Reorganize Codex without deleting fields. Separate personal scratchpad from project research. Standardize empty/loading/no-results/error/selected states and keep valid actions next to their content.

Touchpoints: views/dashboard, views/manuscript, views/codex, views/wiki, views/library, shell/ProjectLibrary.tsx. Audit inconsistent word totals before changing any count semantics.

Done when: long German titles, 116 scenes and 48 characters stay usable at both inspected widths; draft and custom-schema round trips are unchanged; controls don’t imply a selection that does not exist.

Phase 4 · Planning and publication

Apply the shared patterns to the remaining views

Group Timeline controls, make graph/map zoom explicit, add a readable calendar alternative, clarify dialogue confidence, and simplify empty planning states. Add bounded Export options with preview/summary and persistent action. Prioritize Style findings. Group Exposé targets, draft transfer, narration voice setup, language editing, series and Git flows.

Touchpoints: the remaining views/* components listed in the per-screen review. Reuse the existing APIs and algorithms. A true export preview must share the exporter’s layout logic; ship an honest summary first if that cannot be guaranteed.

Done when: actions never detach from fields on a maximized monitor, tables/canvases use available width, and all empty/populated/error states have a valid next step. No unsupported feature or generated statistic is presented as real.

Phase 5 · Background updates and application tools

Separate download from safe installer handoff

Implement the approved update state machine, persistent entry point and per-extension status. Preserve save barriers, backups, detached-window checks and installer token validation. Align Settings, Extensions, About and backups with the same form/action patterns.

Touchpoints: main/appUpdater.ts, main/index.ts, preload/index.ts, renderer bridge types, shell/AppShell.tsx, UpdateDialog.tsx, views/about, views/settings, views/extensions.

Done when: download can complete without blocking writing, installation never races a save, failure leaves the app usable, and Windows/macOS/Linux/Mac App Store handoffs remain truthful.

Phase 6 · Verification, localization and release documentation

Verify the whole desktop workflow before rollout

Run targeted existing regression suites and screenshot comparisons. Add interaction tests for the changed behaviors, not cosmetic snapshots alone. Check de/en/zh-CN, long extension names, UI scaling, real maximization, split/detached panes and keyboard/screen-reader paths.

Documentation: update relevant manual pages and hotkeys only when changed. Before adding Unreleased notes, inspect desktop tags and published changelog sections; consolidate final capabilities once. This review itself changes no desktop behavior and needs no changelog entry.

Done when: the acceptance checklist below passes on supported platforms and user-approved decisions are reflected in the final implementation. Use separate commits/PRs by phase so regressions are isolatable.

Acceptance and regression checks

Layout and interaction

  • Test 1,280 × 800, 1,440 × 960, 1,920 × 1,080 and genuine maximization at 2,560 × 1,440; include 125%, 150% and 200% UI scaling.
  • Title, active book/draft and selected scene remain identifiable. Resize and mode changes preserve selection and scroll appropriately.
  • No whole-window horizontal scroll; data tables/canvases may scroll within labeled regions.
  • At least 4.5:1 normal text; 3:1 meaningful UI graphics/boundaries where required; visible, unobscured focus. Check actual composited glass surfaces on macOS.
  • Tab/Shift+Tab/Escape/Enter, screen-reader names and selected states work; no hover-only essential actions or drag-only operations.
  • Empty, loading, offline, partial, no-results, failure and long-content states have truthful labels and a valid recovery path.

Existing behavior to protect

  • Editor dirty buffers, pending writes, conflict resolution, undo/redo, snapshots, typewriter preferences and focus-peek access.
  • Split panes, detached windows, saved layouts, book/draft switching and project round trips.
  • Custom entities/fields, template ordering, extension-hosted views, locale fallback and user themes.
  • Update saves/barriers/backups and platform handoff; no automatic restart simply because a download finished.
  • Export format fidelity and scope; narration state and active jobs; Git confirmation and remote behavior.
  • Relevant suites include m86-app-update-shutdown, m60-responsive-writing, m63-mode-layout-matrix, ui-scale, settings-navigation, focus-interactions, m66-scene-survives-a-detour and m40-export-artifacts.

How to use the mockup

  1. Open index.html directly in a browser. Keep the CSS and JavaScript files beside it. No server, package install, remote fonts or network connection is needed.
  2. Use the top review strip to select any of the 27 surfaces. Test the empty state and compare the two UI typography directions.
  3. Maximize the browser and resize it down to laptop dimensions. The viewport readout reports the actual available CSS pixels.
  4. Try the mode navigation, chapter/scene selection, manuscript subviews and filters, Codex tabs, calendar agenda, research note save, export format/selection and Settings scope.
  5. Open Updates, try every state, download the simulated update and continue writing while it finishes. Test Tab, Shift+Tab and Escape in dialogs.
  6. Use Design notes for observed issues and Feature coverage for the retained data, controls and documentation inventory. Scene details has four populated sections; Expand all reveals every Context group. The bookshelf supports selection, filtering, cover size and moving a whole project between shelves. Controls that require real backend work open a clearly labeled interaction specification.

The mockup is a design reference, not production UI code or a full emulator. Sample text edits live only in memory and disappear on reload. Other form controls demonstrate layout and control behavior without persisting project settings. Save indicators say “in this preview.” The review worksheet alone uses browser storage.
